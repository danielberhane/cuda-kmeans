# Benchmark harness

## Running the sweep

```bash
make bench-tools          # seq_kmeans, seq_kmeans_omp, gen_points (no CUDA needed)
mkdir -p bench/results    # sbatch fails if --output's directory does not exist
sbatch bench/run_bench.slurm
```

`run_bench.slurm` is configured for GMU's Hopper cluster: partition `gpuq`, a full
A100 80GB (`--gres=gpu:A100.80gb:1`), `--qos=gpu`, CUDA 12.6.3. On another cluster,
re-derive those four settings with:

```bash
sinfo -p <partition> -o "%20P %15N %50G"
scontrol show node <a gpu node> | grep -i gres
module avail cuda
```

The sweep covers the bundled datasets across dimensionality × K, plus an N-scaling
series generated by `gen_points`. It takes the fastest of three runs per configuration
(noise is one-sided — it only ever makes a run slower) and warms up the CUDA context
first, so the first measured run does not absorb the ~100–300 ms of context creation.

Results land in `bench/results/` as two CSVs plus a run log.

## The correctness gate

The harness refuses to let you publish a meaningless number. After the sweep it
compares GPU and CPU iteration counts for every paired configuration:

```
OK: CPU and GPU converge identically on every configuration
```

If they diverge, the two builds are not performing the same computation and any
speedup derived from them is fiction. This gate is what caught the warp-synchronous
reduction bug — the GPU was reporting 6 iterations against the CPU's 31.

## The CPU baseline

`seq_kmeans.c` matches `src/cuda_kmeans.cu` exactly: centroids initialised to the first
K objects, squared Euclidean distance in a float accumulator with no `sqrt`,
convergence at `delta = changed/numObjs <= threshold`, and a 500-iteration cap.

It is deliberately **not** handicapped — built at `-O3`, using the cache-friendly AoS
layout rather than the SoA layout the GPU needs, with an optional OpenMP path so the
harness can report both single-core and all-core figures. Comparing a GPU against a
strawman CPU baseline inflates speedup.

Verified independently: on `points_3d.txt` at K=4 it converges in 31 iterations and
produces centroids bit-identical to a separate reference implementation.

## Scaling datasets

`gen_points` is deterministic given `(seed, N, D)` — xorshift64*, so output is
bit-identical across platforms and libc versions. The generated files are therefore
reproducible and are not committed; at N=5M each is roughly 500 MB.

The bundled datasets are ~100k points, small enough that the convergence loop is
dominated by per-iteration launch and transfer latency rather than arithmetic. A
speedup measured only there understates the kernels.

## Regenerating the diagram

The animated diagram in the top-level README is generated from the same algorithm:

```bash
node tools/verify-trace.mjs        # gate, then
node tools/make-pipeline-svg.mjs   # -> assets/pipeline.svg
```

`verify-trace.mjs` exists so the diagram cannot drift into fiction. It asserts the
engine reproduces every value measured from the real code — grid geometry, the
shared-memory layout region by region, the 31-iteration convergence, the full δ
sequence to five decimals — and that per-block counts sum to the global count on every
iteration. If it fails, nothing generated from that engine should be published.
